### Tightened Security & RLS Policy Review
As requested, I reviewed the RLS security model. The original migration had `USING (true)` public read policies, which would have leaked unshared meetings, transcripts, and action items to the public anon key.

I have updated the policies with a **strict zero-leak RLS model**:

1. **`action_items` Table**:
   * **No public read policy whatsoever.**
   * Action items are strictly private internal operational data. Even if a meeting has a public share clip, action items will return `0` rows / `null` to the public anon key. Only server-side routes (`service_role`) can read or modify them.
2. **`meetings` Table**:
   * Public anon users can **only** read a meeting **if an active `share_clips` record exists for that meeting**:
     ```sql
     CREATE POLICY "Allow public read on shared meetings"
       ON meetings FOR SELECT TO anon, authenticated
       USING (EXISTS (SELECT 1 FROM share_clips WHERE share_clips.meeting_id = meetings.id));
     ```
   * All unshared meetings are completely invisible to the public anon client.
3. **`transcript_lines` Table**:
   * Public anon users can **only** read transcript lines for meetings that have an active share clip.
4. **`share_clips` Table**:
   * Public read is allowed so visitors can look up a shared clip by its unique token.
5. **PostgREST Role Grants**:
   * Explicitly grants schema and table permissions (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) to `service_role`, `anon`, and `authenticated`.
   * For `service_role`, Supabase's `BYPASSRLS` allows server-side API routes to manage all records.
   * For `anon`, PostgreSQL strictly enforces the scoped policies above.

GRANT ALL ON ALL ROUTINES IN SCHEMA public TO anon, authenticated, service_role;

ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON SEQUENCES TO anon, authenticated, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON ROUTINES TO anon, authenticated, service_role;

-- 2. Clean up any previous broad policies
DROP POLICY IF EXISTS "Allow public read on meetings" ON meetings;
DROP POLICY IF EXISTS "Allow public read on transcript_lines" ON transcript_lines;
DROP POLICY IF EXISTS "Allow public read on action_items" ON action_items;
DROP POLICY IF EXISTS "Allow public read on share_clips" ON share_clips;
DROP POLICY IF EXISTS "Allow public read on shared meetings" ON meetings;
DROP POLICY IF EXISTS "Allow public read on shared transcript lines" ON transcript_lines;

-- 3. Ensure Row Level Security is active
ALTER TABLE meetings ENABLE ROW LEVEL SECURITY;
ALTER TABLE transcript_lines ENABLE ROW LEVEL SECURITY;
ALTER TABLE action_items ENABLE ROW LEVEL SECURITY;
ALTER TABLE share_clips ENABLE ROW LEVEL SECURITY;

-- 4. Scoped Public RLS Policies
-- Share clips: public read to lookup by token
CREATE POLICY "Allow public read on share_clips"

### Root Cause & Resolution for the HTTP 504 Error

#### 1. Why Did HTTP 504 (Gateway Timeout) Occur?
1. **Google Gemini Demand Spikes**: During audio processing, if the primary model experienced temporary high demand (HTTP 503), the previous sequential retry loop (`4 attempts × 3 models`) took up to 45–60+ seconds.
2. **Gateway Execution Limits**: Upstream proxies and serverless gateways (such as Vercel or local edge proxies) enforce a strict 15–30 second request timeout. When audio inference took longer than that timeout, the gateway terminated the connection with `504 Gateway Timeout` before the API route could return.
3. **Dev Server Availability**: The local Next.js background process had previously terminated between checkpoints, causing local proxy requests to hang.

---

#### 2. What Was Fixed:

1. **Strict 20-Second Timeout Budget with `Promise.race` ([`lib/ai/summarize.ts`](file:///c:/Users/dell/Desktop/Khizar/Fathom/lib/ai/summarize.ts))**:
   - Audio inference is now capped at **20 seconds max**.
   - If Gemini is delayed or experiences a demand spike, `Promise.race` triggers an immediate fallback to raw recording preservation:
     - The meeting is still safely created in Supabase.
     - The raw audio/video recording is preserved in Supabase Storage.
     - An honest, clear notice is displayed: *"Recording uploaded successfully. Audio transcription took longer than expected; your raw recording is safely preserved."*
     - The API returns HTTP `200 OK` in under 22 seconds, preventing the gateway from ever hitting a 504 timeout.
2. **Prioritized Fast Active Models**:
   - `gemini-3.8-flash` is now called first (which transcribes short recordings in ~3–6 seconds), with immediate fallback to `gemini-3.5-flash`.
3. **Actionable UI Error Messaging ([`components/meeting/UploadMeetingModal.tsx`](file:///c:/Users/dell/Desktop/Khizar/Fathom/components/meeting/UploadMeetingModal.tsx))**:
   - If an edge proxy timeout (HTTP 504) does occur on low-bandwidth connections, the UI now displays helpful guidance (*"The upload gateway timed out while processing audio. Please try with a shorter recording clip (under 2 minutes) or try again."*) instead of a raw HTTP error code.
4. **Dev Server Running Locally**:
